# Security

How ShopOS protects shops' data, what was reviewed before launch, and what is left to do.

## Controls in the application

| Area | How it works | Where |
|---|---|---|
| Passwords | scrypt (N=2¹⁵, r=8, p=1, 64-byte key, per-user salt), constant-time compare, 10–200 characters. A dummy hash for unknown emails, so timing does not reveal which emails have accounts. | `lib/password.ts` |
| Sessions | 32-byte random token in an HttpOnly, SameSite=Lax cookie (`__Host-` prefixed and Secure over HTTPS). Only its SHA-256 is stored. 30 days maximum, 7 days idle. Password reset and disabling a user end their sessions everywhere. | `lib/local-auth.ts`, `lib/local-session.ts` |
| Brute force | Failed sign-ins: 5 per email and 30 per IP per 15 minutes. Sign-ups: 10 per IP per hour. Reset/verification emails: 3 per email and 20 per IP per 15 minutes. Password changes: 5 per user per 15 minutes. | `lib/local-auth.ts` |
| Account discovery | Forgot-password and resend-verification answer the same whether or not the email exists. | `lib/local-auth.ts` |
| Email links | Single-use, hashed, expiring tokens (verify 24 h, reset 1 h, invite 7 days). Verification is a POST, so email scanners that prefetch links cannot use them up. | `lib/local-auth.ts` |
| Cross-site requests | SameSite cookies, plus every write checks the Origin header against the host. Server actions (admin panel) are origin-checked by Next.js. | `lib/local-session.ts` |
| Roles | Owner / manager / cashier, checked on every API route through one guard (`withShop`) and again by the page proxy. Cashiers: POS, dashboard, customers only; refunds need a manager. | `lib/permissions.ts`, `proxy.ts` |
| Shop isolation | Every query is scoped by the signed-in user's shop ID; another shop's records are reported as "not found". Covered by `e2e/tenancy.spec.ts`. | `lib/local-*.ts` |
| Platform admin | `/admin` is a 404 for everyone else. The proxy, every admin page and every admin action check the role independently. | `proxy.ts`, `lib/admin.ts`, `app/admin/session.ts` |
| Subscriptions | Expired or suspended shops are read-only (HTTP 402 on writes) but can still pay and send proofs. | `lib/local-session.ts` |
| Input | Every request body and query is validated with zod (types, lengths, ranges). All SQL uses placeholders; the only interpolated identifiers come from fixed lists. | `app/api/**` |
| Money | Sales, returns, purchases and payments run in transactions with row locks in a fixed order (no overselling, no deadlocks). Sales and returns are idempotent by `client_id`, so retries never double-charge. Payments cannot exceed the balance. | `lib/local-db.ts`, `lib/local-business.ts` |
| Files | Type detected from the file's bytes (not its name), 5 MB limit, random keys. Served only through `/api/files/…` to the same shop (proofs: owner) or the admin, with `nosniff` and a sandbox CSP for images. Payment proofs: 10 per shop per day. | `lib/storage.ts`, `app/api/files/` |
| Emails | All user-supplied text (names, shop names) is HTML-escaped in emails. | `lib/mailer.ts` |

## Controls in the deployment

- **Network:** only nginx publishes ports (80/443). The database, MinIO and the app are reachable only
  inside the Docker network; the MinIO console and Mailpit bind to 127.0.0.1.
- **HTTPS:** Let's Encrypt or a Cloudflare origin certificate; HSTS (1 year) once a trusted
  certificate is in place; `X-Content-Type-Options`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy`;
  `Server: nginx` carries no version; uploads over 6 MB are refused at the edge; sign-in, sign-up and
  email-link endpoints are limited to 30 requests a minute per address in nginx, on top of the app's
  own per-account limits.
- **Visitor IP:** nginx trusts forwarded addresses only from `SHOPOS_TRUSTED_PROXIES` (Cloudflare's
  ranges when proxied). A visitor cannot fake `X-Forwarded-For` or `CF-Connecting-IP` to dodge limits.
- **Containers:** the app runs as a non-root user; every container runs with `no-new-privileges`; the
  app has a memory limit; logs are rotated.
- **Secrets:** generated by the installer, stored only in `.env.production` (mode 600), excluded from
  the Docker build context (`.dockerignore`) and from git (`.gitignore`). The image contains no env files.
- **Server:** ufw firewall (SSH, 80, 443), fail2ban for SSH, automatic security updates, optional
  key-only SSH.
- **Backups:** daily database dump and file archive, 14 days; a failed dump is never stored as a
  backup (it used to be: fixed on 14 Oct 2026).

## Pre-launch review (14 October 2026)

The whole self-hosted code path was read: authentication, sessions, permissions, every API route,
the data layer (sales, returns, khata, suppliers, purchases, expenses, reports, day-end), the platform
admin, file storage, email, the proxy, Docker, the HTTPS proxy and the backup script. Dependencies: Next.js
16.3.3 and React 19.3.0 include the fixes for the 2025 React Server Components vulnerabilities;
nodemailer 10.x is current. Run `npm audit --omit=dev` before each release (the installer does).

Fixed during the review:

| Severity | Finding | Fix |
|---|---|---|
| High | Every production backup since 9 Oct was empty: after a reboot the backup ran before the database was up, and `dump \| gzip` hid the failure. | `scripts/db-backup.sh` waits for the database, checks the dump itself, retries in 5 minutes. |
| High | The Billing page showed placeholder bank details (an example account and IBAN, plus a wallet and WhatsApp number of unknown owner) when `SHOPOS_PAY_*` were unset, so shops could pay the wrong account. | No defaults: unset details are not shown; a neutral note appears instead. |
| Medium | Behind Cloudflare every visitor would share Cloudflare's IPs, so one person's failed sign-ins could lock out everyone. | The HTTPS proxy (now nginx) takes the visitor IP from trusted proxies only (`SHOPOS_TRUSTED_PROXIES`); verified with a spoofing test. |
| Low | Replacing a product's photo deleted the file even when another product still used the same photo. | Deleted only when no product references it; test added. |
| Low | An old empty SQLite file was committed (`.data/`). | Removed from git (no personal data was in it). |

Verified with new tests: every button on every screen for every role (`e2e/buttons.spec.ts`), and
double-clicks on every money button record once (`e2e/double-submit.spec.ts`).

## Known gaps and recommendations

- **Off-site backups** are not automatic yet: copy `backups/production` off the server (see
  [deployment.md](deployment.md#backups)).
- **No two-factor sign-in.** For the platform admin, use a long unique password; 2FA is a good next feature.
- **Invitations and sign-ups send email to any address** within the rate limits; watch for abuse in
  the admin panel (many shops from one IP), and lower `SHOPOS_SIGNUP_LIMIT` if needed.
- **Customer and supplier payments** have no idempotency key (they rely on the button disabling,
  which the double-submit test proves). A network retry by a custom client could record twice.
- **Product image links** may point to external `https://` images; viewers' browsers then fetch them.
- **WhatsApp numbers** saved without a country code are assumed to be Pakistani (+92).
- Legacy hosted-mode (Supabase) code is still in the repository; it is unused when
  `SHOPOS_STORAGE=mariadb` and should be removed.

## Personal data

ShopOS stores shop owners' and staff's names, emails and password hashes; shops' customers' and
suppliers' names, phone numbers and addresses; sales and payment records. Selling to the UK/EU makes
you the data **processor** for your shops (they are the controllers): publish a privacy policy and
terms, keep data in the EU/UK-friendly region you host in, delete a shop's data when asked (the admin
can suspend; deletion is a database operation today), and report breaches without delay.

## Reporting a vulnerability

Email the platform admin address with details and steps to reproduce. Do not test against other
shops' data.
